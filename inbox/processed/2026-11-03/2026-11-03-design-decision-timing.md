# 후보: 화면이 있는 작업은 디자인을 정하는 시점을 박아 두고, 정하기 전엔 화면을 만들지 않는다

- **출처:** sonmat-lab MVP(2026-11-02~03, Flutter 3.47.9). 사용자 지적(2026-11-03): "우리 디자인은 정하지도 않았는데 이미 구현이 되어 버린 거야?", "이게 매번 반복되는 걸 보니 dev-convention에 디자인 선택 시점을 좀 더 명확하게 해야 할 것 같아" — 다른 프로젝트에서도 반복된다는 사용자 증언.
- **dev-conventions에 지금 있는 것:** 없다. `global/`·`project/AGENTS.template.md`·`install/apply-conventions.md`에서 디자인·목업·시안 검색 0건.
  가까운 것은 inbox `2026-10-19-ui-color-role-pairs.md`(색을 역할 토큰으로)인데, 디자인을 **코드에 어떻게 담나**이지 **언제 정하나**가 아니다.

## 관찰된 실패

- 설계 문서(spec)에서 기능·흐름은 사용자와 정했고 「미정(사용자 결정 필요)」 칸은 「없음」이었다. 시각 방향(분위기·색·글꼴)과 화면 배치는
  **항목 자체가 없어서 빈칸으로도 드러나지 않았다.**
- 시안을 만든 건 논쟁이 된 요소 하나(요리 모드 타이머 표시 — 목업 여러 안 비교)뿐이다.
- 구현 계획 17개 task가 모든 화면을 Flutter 기본 Material 3 + 에이전트가 고른 기준색 하나로 만들었다. 화면 배치도 구현자가 정했다.
- MVP 뒤 to-do(메뉴 지우기·라벨 사진·이름 바꾸기)도 "진행해 줘" 승인만으로 에이전트가 버튼 위치를 정해 붙였다.
- 사용자는 기능 9개 화면이 다 만들어진 뒤에야 알아챘다.
- 규칙이 못 막은 이유: 개인 지침의 「범위·스택·완료 조건 합의 후 승인」에 디자인이 없고, superpowers brainstorming도 디자인 결정을 따로 요구하지 않는다.
  「필요한 파라미터가 없으면 묻는다」(always-on)도 디자인에 해당하는 파라미터가 없어 걸리지 않았다.

## 승격안 (`agent-workflow`의 새 절 + 프로젝트 파라미터 — always-on 줄은 늘리지 않는다)

1. **시점:** 사용자에게 보이는 화면이 있는 새 제품·기능은 기능·흐름을 정한 직후(spec), 구현 계획(plan)을 쓰기 전에 디자인을 정한다.
   정할 것: 시각 방향(분위기·색·글꼴·밀도)과 주요 화면 배치.
2. **파라미터 `design`:** 프로젝트 AGENTS.md에 `design: <디자인 결정 문서 경로> | 미정 — 화면 구현 전에 정한다`.
   always-on의 「필요한 파라미터가 없으면 추측하지 말고 묻는다」가 그대로 집행 장치가 된다 — 줄이 없거나 `미정`이면
   테마·새 화면·배치 변경을 시작하지 않고 시안부터 낸다. `project/AGENTS.template.md`에 줄을 추가하고 `/apply-conventions`가 물어 채운다.
3. **spec의 디자인 칸:** spec에 「디자인」 항목을 둔다. 정했으면 결정과 시안 경로, 안 정했으면 「미정」에 올린다.
   디자인 칸이 비어 있으면 「미정: 없음」이라고 쓰지 않는다.
4. **정하는 방법:** 같은 화면을 다른 방향으로 그린 시안 2~3개를 사용자가 열 수 있는 미리보기로 보여 주고 고르게 한다.
   고른 것은 `decisions`에 결정 기록으로 남기고, 디자인 값(색·글꼴·간격)은 코드 한 곳(테마)에 둔다 → `2026-10-19-ui-color-role-pairs.md`와 이어진다.
5. **작은 UI 변경:** 정해진 디자인 안에서 기존 패턴을 따르는 추가(버튼·칸 하나)는 승인된 작업 범위 안이다.
   새 화면·새 배치·새 패턴은 구현 전에 배치를 한 줄로 확인받는다. 확인 없이 만들었으면 보고에 「배치는 에이전트가 정했다」를 밝히고 화면(미리보기·스크린샷)을 함께 준다.
6. **디자인 없이 먼저 만들어야 할 때(프로토타입):** 사용자가 명시적으로 동의한 경우만. 기본 테마로 두고 「디자인 미정」 to-do를 등록해 빈칸이 사라지지 않게 한다.

재사용: 화면이 있는 모든 프로젝트(Flutter·웹). 같은 일이 있었던 다른 프로젝트 사례가 확인되면 출처에 덧붙인다.
