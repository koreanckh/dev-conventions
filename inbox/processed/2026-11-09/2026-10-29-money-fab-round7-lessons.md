## 1. 외부 API 수집기는 원본 응답(필요한 열)을 저장하고 파싱은 따로 둔다 (coding-conventions · 데이터 수집)

**관찰:** OpenDART 재무 주요계정 수집기가 응답을 받자마자 요약 표(종목·기간당 한 줄)로 바꿔 저장했다. 수집 뒤 점검에서 파싱 규칙을 세 번 고쳤다(기간 말일을 재무상태표 날짜로, 자본총계가 빠진 응답은 자산 − 부채로, 금융회사 판정용 업종 코드). 원본이 없어 고칠 때마다 전 종목을 다시 받았다(1,277번 호출 × 3, 11~24분씩). 하루 호출 한도가 있는 API라 다음 단계 수집 일정까지 밀렸다.

**후보 규칙:** 하루 한도나 긴 시간이 드는 외부 API 수집은 응답 원본(최소한 쓰는 계정·필드의 원문 행)을 저장하고, 요약·파생 값은 원본에서 다시 만드는 함수로 분리한다. 파싱을 고쳐도 재수집 없이 다시 만든다.

## 2. 출처의 성질을 한 시점만 실측해 전 기간 가정으로 쓰지 않는다 — 수집 뒤 전 기간에 검사한다 (agent-workflow · 실측)

**관찰:** "금융회사는 DART 주요계정에 0행"을 2017 사업보고서 한 번으로 확인하고 결정 기록에 "금융업은 저절로 빠진다"고 적었다. 실제로는 2023 3분기 보고서부터 금융회사도 나온다. 그 결과 라운드 결과(표본 외 마지막 1년)에 은행·보험이 가치 순위에 섞인 채로 해설까지 쓰고, 병합 직전에야 찾았다.

**후보 규칙:** 실측으로 얻은 "출처의 성질"(없는 값, 범위, 형식)을 설계 가정으로 쓰면, 전체 수집 뒤 그 가정을 전 기간에 검사하는 점검(예: 기간별로 그 집단의 행 수)을 같이 돌리고 결과를 실측 기록에 남긴다.

## 3. `git pull --rebase && <편집>` 뒤 줄에 commit을 두면 편집 없이 커밋된다 (handoff · docs-branch 커밋)

**관찰:** docs-branch 워크트리에서 `git pull -q --rebase && python3 <to-do 수정>` 다음 줄에 `git add … && git commit`을 뒀다. 워크트리에 커밋 안 한 파일이 있어 pull이 실패했고, `&&`로 묶인 to-do 수정만 건너뛴 채 다음 줄의 add/commit/push는 그대로 돌아 "to-do 갱신"이라는 커밋에 to-do가 빠졌다. 커밋 통계를 보고 알아챘다.

**후보 규칙:** docs-branch에 올릴 때는 편집 전에 pull을 따로 돌려 성공을 확인하거나, 스크립트에 `set -e`를 둔다. 커밋 뒤 `git show --stat HEAD`로 의도한 파일이 들어갔는지 본다.
