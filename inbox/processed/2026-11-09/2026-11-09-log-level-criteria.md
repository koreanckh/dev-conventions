# 후보: 로그 레벨은 「그 줄을 쓰는 시점의 사건」과 「누가 조치해야 하나」로 정한다 (2026-11-09)

- **출처:** 회사 팀 레포 Django API(`~/dev/common-api`) PR #92 — 운영 오류 로그 패널을 보다가 로그 호출 약 300곳을 점검·정리
- **승격 대상:** `coding-conventions` 「공통 규칙」에 `### 로그 레벨` 절 신설 (지금 로그 레벨 규칙이 없다)

## 관찰한 실패

1. **오류 패널이 규칙대로 한 거절로 차 있었다.** 파일 검증 API가 중복 파일을 찾을 때(그 API의 정상 결과), 잘못된 암호화 키·없는 프리셋 ID로 4xx를 돌려줄 때마다 ERROR를 찍었다. ERROR 패널만 보는 운영에서 진짜 오류가 이 소음에 묻혔다.
2. **진짜 실패는 레벨이 아예 없었다.** Slack 알림 전송 실패·스케줄러 시작 실패를 `print`로 찍었다. Slack 쪽은 호출한 view가 예외를 로그 없이 삼켜서 남는 기록이 print 한 줄뿐이었다. 레벨이 없으니 ERROR 패널에도 오류 로그 파일에도 안 잡힌다.
3. **결과로 레벨을 정하려는 유혹.** 외부 API 500 ERROR 바로 옆에 찍힌 업로드 요청 접수 INFO를 보고 「이것도 ERROR여야 하지 않나」는 질문이 나왔다. 접수 시점엔 결과를 모르고, 실패는 실패 지점에서 따로 ERROR로 남는다. 접수 로그를 ERROR로 올리면 정상 요청마다 ERROR가 찍힌다.
4. **기준대로 내리면 신호를 잃는 경우.** 업로드 뒤 부가 기능(최근 활동 등록)의 외부 API 실패는 본 작업이 성공했으니 기준상 WARNING이다. 그런데 WARNING을 보는 패널이 없었고, 바로 그 ERROR로 외부 API 장애를 알아챘다. ERROR로 남겼다.
5. (부수) 레벨을 문자열로 받는 손수 만든 `log_message(level, msg)` 헬퍼가 `info/error/debug`만 허용해서, `"warning"`을 넘기면 `Unknown log level: warning. Message: ...`로 찍혔다. 같은 헬퍼가 서비스 다섯 곳에 복사돼 있었다.

## 승격안 (`### 로그 레벨`)

- 레벨은 **그 줄을 쓰는 시점의 사건**으로 정한다. 요청의 최종 결과로 정하지 않는다. 실패는 실패한 지점에서 따로 남기고, 줄끼리는 trace_id 같은 요청 식별자로 잇는다.
- **ERROR** = 우리 시스템이나 외부 의존성이 실패해서 사람이 조치해야 하는 일. **WARNING** = 규칙대로 거절한 요청(4xx), 실패했지만 대체 처리로 넘어간 일. **INFO** = 정상 흐름의 주요 사건(요청 접수·상태 변경·완료). **DEBUG** = 항목별 세부 정보(운영에서 꺼짐).
- 클라이언트 입력을 규칙대로 거절한 것은 ERROR가 아니다. 검증 API가 찾아낸 문제(중복 등)는 그 API의 정상 결과라 INFO다.
- 실패를 `print`로 남기지 않는다 — 레벨이 없어 오류 패널·오류 로그 파일 어디에도 안 잡힌다. 예외를 삼키는 곳(잡고 응답만 돌려줌)에는 반드시 로그를 남긴다.
- 운영에서 재현에 필요한 입력값(요청 본문 등)은 DEBUG가 아니라 INFO로 남긴다. DEBUG는 운영에서 꺼져 있다.
- 레벨을 내리기 전에 **그 레벨을 실제로 누가 보는지** 확인한다. WARNING을 보는 곳이 없으면, 조치가 필요한 외부 의존성 실패는 ERROR에 둔다.
