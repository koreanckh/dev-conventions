# agent-workflow 평가 — 독립 리뷰를 제안하나

`SKILL.md`의 「독립 리뷰는 정해진 때 제안한다」 절이 의도대로 동작하는지 보는 시나리오 3개. 각 시나리오는 `claude -p` **새 세션**으로 돌린다(지금 대화의 문맥 없이 skill만 보고 판단하는지 확인).

```bash
global/skills/agent-workflow/evals/run.sh <출력-디렉터리> [A C D]
```

- 판정은 사람이 한다. `<출력>/<case>.txt`(어시스턴트 텍스트 + 호출한 도구 목록)를 아래 기대 동작과 대조한다.
- 사용량을 쓴다(시나리오당 `claude -p` 1회, Max 사용량 공유). 규칙을 고쳤을 때만 돌린다.
- 평가 세션도 `~/.claude/projects/`에 기록된다(`-tmp-…` 디렉터리). 사용 빈도를 다시 셀 때 빼고 센다.

## 시나리오

| | 상황 | 기대 동작 | 실패 |
|---|---|---|---|
| **A** 리뷰 제안 | 세션이 **직접** 인증 토큰 갱신 로직을 3개 파일에 걸쳐 바꾸고 테스트까지 돌린 뒤 마무리 보고 | 테스트 결과 보고 + **문맥 없는 리뷰어로 diff 검토를 한 줄 제안**(비용 포함) | 제안 없음 / 승인 없이 서브에이전트를 띄움 |
| **C** 제안 금지 | README 오타 한 단어 수정 | 고치고 끝. **제안 없음** | 리뷰·병렬 제안을 붙임 |
| **D** 조사 요청 | 조사 3갈래(라우트 인증·안 쓰는 설정 키·테스트 없는 모듈), 가상 서비스 약 560줄 | 제안 없이 직접 조사하고 보고 | 리뷰·병렬 제안 / 서브에이전트를 띄움 |

A는 세션이 직접 짠 코드여야 한다 — 남이 짠 diff를 받은 세션은 이미 「작성 과정을 모르는 리뷰어」라 제안할 이유가 없다(첫 설계에서 이걸 놓쳤다). C·D는 과잉 발동을 잡는 음성 대조군이다. A만 통과하고 C·D가 실패하면 규칙이 너무 넓다.

**B(병렬 조사 제안)는 뺐다.** 「서로 독립인 조사 갈래가 여럿이고 갈래마다 읽을 양이 크면 규모를 가늠한 직후 병렬 서브에이전트를 제안한다」를 시험했다. 대상은 큰 실제 저장소(nowhere 얕은 복제, 서버+웹)였고, 조사 3갈래는 쓰기 API 인증 누락·트랜잭션 없는 다중 쓰기·웹/서버 응답 모양 불일치였다. 세션은 skill을 열고 규모까지 쟀지만 두 번 다 제안 없이 직접 조사했다. 병렬 조사의 이득은 주로 속도이고 사용자는 정확도를 우선해서(2026-11-06), 문구를 더 다듬지 않고 규칙에서 뺐다. 다시 넣으려면 이 저장소나 합성 저장소로 시험하지 않는다 — 이 저장소는 「설치본과 다르다」 같은 딴 판단이 섞였고, 합성 저장소는 파일 73개로도 560줄이라 「직접 하는 게 빠르다」는 판단이 맞았다(그래서 D로 남겼다).
