# 장시간 작업

한 번 도는 데 수십 분 이상 걸리는 수집·배치·학습 작업의 규칙. 이런 작업은 실패가 늦게 드러나고, 드러나는 순간 그때까지 쓴 시간이 통째로 날아간다. 아래 규칙은 전부 **실패를 일찍 보이게 하고, 실패해도 처음부터 다시 하지 않게** 하려는 것이다. 프로젝트마다 달라지는 값은 없다 — 실행 위치·리소스 한도는 프로젝트가 아니라 호스트의 사실이다.

## 원칙

### 실패해도 처음부터 다시 하지 않는다

- **중간 결과를 N건마다 파일에 쓰고, 다시 돌리면 받은 건은 건너뛴다(재개 가능).** 결과를 끝에서 한 번만 쓰면 마지막 건에서 죽어도 전부 잃는다. money-fab의 배당 수집(3,562종목)은 40분을 돈 뒤 죽어 결과를 전부 잃었고, 다시 받는 데 56분이 더 들었다(2026-10-29).
- **외부 API 응답은 원본(최소한 쓰는 필드의 원문 행)을 저장하고, 요약·파생 값은 원본에서 다시 만드는 함수로 분리한다.** 파싱 규칙은 수집 뒤에 거의 반드시 고치게 되는데, 원본이 없으면 고칠 때마다 다시 받는다. 하루 호출 한도가 있는 API면 다음 수집 일정까지 밀린다(money-fab: OpenDART 재무 수집의 파싱을 세 번 고치며 1,277회 호출 × 3, 2026-10-29).

### 실패를 일찍 보이게 한다

- **전체 실행 전에 작은 표본(수십 건)으로 한 번 끝까지 돌린다. 표본에 「결과가 빈 항목」(이력 0건, 응답 0행)을 일부러 섞는다.** 위 40분짜리 실패의 원인(빈 리스트로 열을 고르면 0열이 된다)은 작은 입력 테스트에 빈 항목이 없어서 못 잡았다.
- **스레드 풀에 작업을 전부 미리 `submit`했으면 첫 예외에서 멈추게 하거나, 항목 단위로 예외를 잡아 실패 목록에 모은다.** Python `with ThreadPoolExecutor() as ex:` 블록을 예외가 빠져나갈 때 `shutdown(wait=True)`가 **이미 제출된 나머지 작업을 다 기다린 뒤에야** 예외를 올린다. 첫 예외에서 `ex.shutdown(cancel_futures=True)`로 남은 작업을 버린다. `with` 블록이 예외를 곧바로 올려 줄 거라고 기대하지 않는다.
- **출력을 파일로 돌리는 Python 작업은 `PYTHONUNBUFFERED=1`(또는 `python -u`)로 돌린다.** 터미널이 아닌 곳으로 가는 stdout은 블록 버퍼라, 도중에 죽으면 버퍼에 남은 진행 로그도 같이 사라져 어디까지 갔는지 모른다(money-fab: 실행 세 번을 날렸다, 2026-10-28). 사용자에게 주는 실행 명령에도 넣고, 진행 로그를 찍는 CLI는 `print(..., flush=True)`를 기본으로 한다.

### 실측한 가정은 전 기간에 다시 검사한다

- 실측으로 얻은 **출처의 성질**(없는 값, 범위, 형식)을 설계 가정으로 쓰면, 전체 수집 뒤 그 가정을 **전 기간에 검사하는 점검**(예: 기간별로 그 집단의 행 수)을 같이 돌리고 결과를 실측 기록에 남긴다. 한 시점의 실측은 그 시점의 사실일 뿐이다.
- 왜: 「금융회사는 DART 주요계정에 0행」을 2017 사업보고서 하나로 확인하고 결정 기록에 「금융업은 저절로 빠진다」고 적었는데, 2023 3분기 보고서부터는 금융회사도 나왔다. 은행·보험이 순위에 섞인 채 결과 해설까지 쓴 뒤 병합 직전에야 찾았다(money-fab, 2026-10-29).

### 공유 서버에선 하드 상한으로 가둔다

에이전트 터미널과 무거운 작업이 같은 systemd 사용자 슬라이스에 사는 서버의 규칙이다.

- 무거운 작업은 **하드 상한**으로 돌린다. 넘으면 그 작업만 커널 OOM으로 죽는다(exit 137).
  ```sh
  systemd-run --user --scope -p MemoryMax=<실측 최고치+여유> -p MemorySwapMax=0 -p CPUQuota=<n>% \
    nice <명령>
  ```
- **`MemoryHigh`·스왑으로 「넘으면 느려지게」 하지 않는다.** 압박이 오르면 systemd-oomd는 회수량이 큰 **다른** cgroup을 고른다 — chois에서 시험 프로세스가 아니라 Claude Code 터미널 pty 두 개가 죽었다(2026-10-27). `CPUQuota`는 느려질 뿐 안전했다.
- 하드 상한 안에서도 계정 전체 압박은 오른다. 오래 도는 작업엔 `memory.pressure`(cgroup v2)를 주기적으로 읽어 높은 압박이 이어지면 작업을 멈추는 감시기를 붙인다.

## 셋업 / 값

- sudo 없이 `systemd-run --user`로 상한을 걸려면 사용자 슬라이스에 cpu·memory 컨트롤러가 위임돼 있어야 한다. 확인: `cat /sys/fs/cgroup/user.slice/user-$(id -u).slice/user@$(id -u).service/cgroup.controllers`에 `cpu`·`memory`가 있다.
- 감시기 임계값의 실측 예(chois, dev 계정): 2초마다 읽어 `some` > 30 · `full` > 20이 3번 이어지면 멈춘다. 다른 호스트에선 다시 잰다.

## 주의 / 알려진 불일치

- 관찰은 전부 money-fab(Python, 2026-10-28~29)에서 나왔다. 다른 언어의 스레드 풀·버퍼링 기본 동작은 이 문서가 확인하지 않았다 — 원칙(재개·빨리 멈추기·버퍼 비우기)은 같고, API는 그 언어 문서로 확인한다.
- 장기 실행이 작업 트리를 읽는 동안 그 clone의 체크아웃을 바꾸지 않는다. 그동안 handoff·to-do를 어디서 고칠지는 실행 전에 정한다 → [작업 인계](../handoff/SKILL.md)의 "`docs-branch` 문서를 어디서 고치나".
- 서버에서 띄운 프로세스를 끌 때 `pkill -f`를 쓰지 않는다 → [코딩 컨벤션](../coding-conventions/SKILL.md)의 "셸 스크립트".

## 필요한 프로젝트 파라미터

- 없음. 중간 저장·원본 응답 경로는 프로젝트 코드가 정하고, 리소스 한도는 실행하는 호스트에서 잰다.
